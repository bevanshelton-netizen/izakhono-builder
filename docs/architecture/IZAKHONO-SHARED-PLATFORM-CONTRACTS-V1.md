# IZAKHONO Shared Platform Contracts
## Version 1.0 — Logical contracts and interoperability baseline

- **Status:** Proposed; documentation-only contract specification
- **Date:** 26 November 2026
- **Depends on:** [IZAKHONO Intelligent Operating Ecosystem Architecture V1](./IZAKHONO-INTELLIGENT-OPERATING-ECOSYSTEM-ARCHITECTURE-V1.md)
- **Authority:** Subject to owner review and approval. This document does not assert that the contracts are implemented or authorise production changes, expenditure, infrastructure provisioning or service activation.

---

## 1. Purpose and scope

This specification defines the minimum shared contracts that allow IZAKHONO product domains to interoperate without collapsing their data ownership or security boundaries.

It establishes common vocabulary and proposed logical shapes for:

1. tenant and actor context;
2. resource identity and ownership;
3. event envelopes and delivery semantics;
4. evidence provenance and lifecycle;
5. FORTRESS authorisation and approval decisions;
6. runtime identity and execution-environment bindings;
7. idempotent commands and standard errors;
8. audit records and correlation;
9. contract versioning, compatibility and conformance.

These are design contracts, not deployed APIs, database migrations, queue definitions or executable JSON Schemas. Before implementation, each contract must be translated into machine-validated schemas, API specifications, policy tests and domain-specific acceptance tests.

## 2. Normative language

The words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT** and **MAY** express requirement strength.

- MUST / MUST NOT: mandatory interoperability or safety requirement.
- SHOULD / SHOULD NOT: expected default; deviations require a documented reason.
- MAY: optional capability.

A service is not conformant merely because its payload resembles an example. It must satisfy the semantic, security, lifecycle and failure-handling requirements in this document.

## 3. Contract principles

- **Explicit context:** tenant, actor, purpose and correlation context must be explicit and verified.
- **No ambient authority:** a caller's identity does not automatically authorise every action available to a service.
- **Domain ownership:** each product domain remains authoritative for its own business records.
- **Evidence separation:** observation, interpretation, recommendation, decision, action and outcome are different record types/states.
- **Least privilege:** permissions are scoped to action, resource, tenant, purpose and time where applicable.
- **Fail closed:** missing, malformed, expired or unverifiable authority/runtime context must not be silently accepted.
- **No secret propagation:** credentials and secret values must not appear in event envelopes, audit payloads, URLs or ordinary logs.
- **Idempotent side effects:** retryable commands must define deduplication behaviour.
- **Traceable change:** important transitions must be correlatable to actor, policy, source revision and evidence.
- **Versioned evolution:** contracts change through explicit versions and compatibility tests.

## 4. Canonical identifiers

Identifiers are opaque strings with a documented namespace and lifecycle. Consumers MUST NOT infer identity, authority, tenant ownership or ordering from an identifier's text.

| Identifier | Purpose |
|---|---|
| `tenant_id` | Stable identifier for an organisation/customer tenant |
| `actor_id` | User, service, agent or system actor identity |
| `principal_id` | Authenticated security principal presented to FORTRESS |
| `resource_id` | Domain-owned resource identifier |
| `event_id` | Unique event identifier |
| `command_id` | Unique command/request identifier |
| `task_id` | AI Workforce task identifier |
| `approval_id` | Approval workflow record |
| `policy_id` / `policy_version` | Policy identity and immutable evaluated version |
| `correlation_id` | End-to-end workflow correlation |
| `causation_id` | Immediate event/command that caused this record |
| `evidence_id` | Evidence record identifier |
| `runtime_binding_id` | Runtime-to-execution-environment binding record |
| `execution_environment_id` | Separately managed infrastructure environment identifier |

Identifiers MUST be generated by an approved authority and MUST NOT contain secrets or unnecessary personal information. Tenant IDs and resource IDs supplied by callers must be checked against authenticated membership and resource ownership.

## 5. Tenant and actor context

### 5.1 Tenant context

Every tenant-scoped command, query, event, evidence record, approval and audit entry MUST carry or resolve a verified tenant context.

Proposed logical shape:

```json
{
  "tenant_id": "tn_example",
  "tenant_context_version": "1",
  "purpose": "support.case_resolution",
  "environment": "production"
}
```

The example identifier is illustrative only.

Rules:

- Tenant context MUST be derived from an authenticated session/service identity and validated membership or service grant.
- A caller-supplied `tenant_id` is a selector, not proof of membership.
- Cross-tenant access MUST require an explicit, narrowly scoped FORTRESS policy grant and an auditable reason.
- System-wide operations MUST use a distinct privileged scope; they MUST NOT simulate tenant membership.
- Background jobs MUST retain the initiating tenant and actor context or use a separately authorised service identity with explicit delegation metadata.
- Missing tenant context on a tenant-scoped operation MUST be rejected.

### 5.2 Actor context

Proposed logical shape:

```json
{
  "actor": {
    "actor_type": "user",
    "actor_id": "usr_example",
    "principal_id": "prn_example",
    "on_behalf_of": null
  }
}
```

Allowed actor types are initially: `user`, `service`, `agent`, and `system`. Additional types require a versioned vocabulary change.

For delegated work, `on_behalf_of` identifies the delegating actor and MUST NOT be interpreted as an automatic transfer of that actor's full permissions. The effective permission set is the intersection of the delegate's authority, the delegator's grant and the applicable policy.

Agent identity MUST be distinct from the human who initiated a task. Logs and audit records must retain both identities where relevant.

### 5.3 Purpose and data classification

Purpose is a controlled vocabulary describing why the data is accessed or processed. It is not a free-form justification for bypassing policy.

Data classification should use a centrally governed vocabulary, initially:

- `public`
- `internal`
- `confidential`
- `restricted`

Domain-specific sensitivity labels MAY refine these classes. A more restrictive label takes precedence. Classification does not replace access control.

## 6. Resource ownership and access context

Every domain-owned resource MUST have an authoritative owning domain and tenant scope where applicable.

Proposed logical reference:

```json
{
  "resource": {
    "resource_type": "experience.case",
    "resource_id": "case_example",
    "owner_domain": "experience",
    "tenant_id": "tn_example"
  }
}
```

A resource reference is not a capability token. Possession of an ID does not authorise read or write access. Services MUST check ownership and FORTRESS policy at the point of access and again before consequential mutations where state or authority may have changed.

## 7. Common event envelope

### 7.1 Proposed envelope

All cross-domain events MUST use a common envelope or an explicitly mapped transport equivalent.

```json
{
  "event_id": "evt_example",
  "event_type": "experience.case.resolution_recorded",
  "schema_version": "1.0",
  "occurred_at": "2026-11-26T05:00:00Z",
  "recorded_at": "2026-11-26T05:00:01Z",
  "tenant_id": "tn_example",
  "actor": {
    "actor_type": "user",
    "actor_id": "usr_example",
    "principal_id": "prn_example"
  },
  "purpose": "support.case_resolution",
  "classification": "confidential",
  "source": {
    "domain": "experience",
    "service": "case-management",
    "version": "1.0"
  },
  "correlation_id": "cor_example",
  "causation_id": "cmd_example",
  "resource": {
    "resource_type": "experience.case",
    "resource_id": "case_example"
  },
  "payload": {
    "resolution_status": "recorded"
  },
  "provenance": {
    "method": "domain_event",
    "source_revision": "revision-reference"
  }
}
```

All values are illustrative. Payload schemas are owned and versioned by the emitting domain.

### 7.2 Envelope requirements

- `event_id` MUST be unique for the logical event.
- `event_type` MUST use a stable, namespaced vocabulary such as `signal.observation.recorded`.
- `schema_version` MUST identify the payload contract version.
- `occurred_at` is when the source-domain fact occurred; `recorded_at` is when the event was recorded. Both MUST be UTC timestamps.
- `tenant_id` MUST be present for tenant-scoped events.
- `actor` MUST identify the actor responsible for the originating action. System-generated events MUST identify the service/system actor.
- `purpose` and `classification` MUST be set according to policy.
- `source` MUST identify the emitting domain and service.
- `correlation_id` SHOULD persist across the whole workflow; `causation_id` SHOULD identify the immediate cause.
- `resource` MUST identify the primary affected resource where one exists.
- `payload` MUST validate against the schema registered for `event_type` and `schema_version`.
- `provenance` MUST identify collection/derivation origin where relevant.
- Secret values, authentication tokens, private keys and raw credentials MUST NOT be included.
- Personal data SHOULD be minimised; sensitive content SHOULD be referenced through an authorised domain API rather than copied into broad event streams.

### 7.3 Delivery semantics

The platform MUST NOT claim exactly-once delivery unless the selected transport and end-to-end processing design actually provide it. Consumers SHOULD assume at-least-once delivery where retries are possible.

Consumers MUST be idempotent for duplicate `event_id` values. Deduplication retention MUST cover the maximum supported retry/replay window. Event ordering is not guaranteed globally; consumers that require ordering MUST use an explicit aggregate/resource sequence or version.

Publishers MUST define retry, backoff, dead-letter, replay and reconciliation behaviour. Poison messages MUST be quarantined with diagnostic metadata and without leaking sensitive payloads. Replays MUST preserve original event identity and provenance while recording replay metadata separately.

## 8. Evidence contract

### 8.1 Evidence lifecycle

Evidence is typed and must not be silently promoted from one category to another.

| Type | Meaning | Required distinction |
|---|---|---|
| Observation | Directly collected or measured fact | Source, collection context, timestamp |
| Interpretation | Analysis derived from observations | Method, input evidence, confidence/limitations |
| Recommendation | Proposed action | Rationale, expected outcome, uncertainty |
| Decision | Authorised choice | Decision-maker or policy, authority, time |
| Action | Attempted or completed operation | Executor, approval, result and execution reference |
| Outcome | Measured consequence | Measurement method, window and source |

### 8.2 Proposed evidence reference

```json
{
  "evidence_id": "evd_example",
  "evidence_type": "observation",
  "tenant_id": "tn_example",
  "domain": "signal",
  "source_ref": "connector-or-domain-record-reference",
  "observed_at": "2026-11-26T05:00:00Z",
  "collected_at": "2026-11-26T05:00:02Z",
  "method": "documented_collection_method",
  "context": {
    "market": "ZA",
    "language": "en",
    "platform": "example-platform"
  },
  "confidence": {
    "score": null,
    "scale": null,
    "explanation": "No calibrated score assigned"
  },
  "limitations": [],
  "classification": "internal"
}
```

Confidence scores MUST NOT be fabricated or treated as comparable across methods without calibration. If no validated scoring method exists, record no score and explain the limitation.

For AI-answer observations, preserve the exact prompt, response, platform/model, collection timestamp, country, language, browsing/retrieval conditions and cited sources where permitted. A single response MUST NOT be represented as a universal or stable ranking.

### 8.3 Evidence integrity

Evidence records SHOULD be append-oriented. Corrections SHOULD create a superseding record with a reason and reference to the prior record rather than silently rewriting history. Retention and deletion obligations remain applicable; append-only design does not override lawful deletion requirements.

Derived interpretations MUST reference the input evidence IDs and method/version. Recommendations MUST reference their supporting interpretations/evidence. Decisions and actions MUST reference the recommendation or request they address, where applicable.

## 9. FORTRESS authorisation contract

### 9.1 Policy evaluation

All protected operations MUST be authorised through the approved FORTRESS policy boundary. Product services MUST NOT implement hidden permission bypasses.

Proposed request:

```json
{
  "principal": {
    "principal_id": "prn_example",
    "actor_type": "agent",
    "actor_id": "agt_example"
  },
  "tenant_id": "tn_example",
  "action": "experience.case.assign",
  "resource": {
    "resource_type": "experience.case",
    "resource_id": "case_example",
    "owner_domain": "experience"
  },
  "purpose": "support.case_resolution",
  "context": {
    "correlation_id": "cor_example",
    "requested_at": "2026-11-26T05:00:00Z"
  }
}
```

Proposed decision:

```json
{
  "decision_id": "pdec_example",
  "decision": "deny",
  "reason_code": "approval_required",
  "policy_id": "pol_experience_case",
  "policy_version": "3",
  "evaluated_at": "2026-11-26T05:00:00Z",
  "expires_at": null,
  "approval_id": "apr_example",
  "obligations": [],
  "audit_ref": "aud_example"
}
```

The example is a deny decision illustrating a gated action, not a default policy for all case assignments.

### 9.2 Decision requirements

- Default decision MUST be deny when policy is absent, evaluation fails, context is incomplete or authority cannot be verified.
- Decisions MUST be scoped to principal, tenant, action, resource and purpose.
- A permit MUST have a bounded validity period where practical; long-lived reusable permits SHOULD be avoided.
- The policy ID and immutable policy version MUST be recorded.
- Obligations such as redaction, rate limits, human approval or constrained fields MUST be enforced by the calling service before execution.
- A policy decision is not proof that the operation succeeded.
- Services MUST re-evaluate authority when a material state change, delay or scope change invalidates the original decision.
- Policy evaluation and enforcement outcomes MUST be auditable.

### 9.3 Risk tiers and approvals

The following is a proposed baseline; each product must map its actions to these tiers and FORTRESS policy.

| Tier | Example | Default control |
|---|---|---|
| T0 — Read | Read permitted tenant-scoped data | Authenticated, scoped read permission |
| T1 — Analyse | Summarise, classify, compare, recommend | Scoped data access; provenance retained |
| T2 — Reversible internal write | Create draft, internal case, proposed change | Explicit write permission; audit |
| T3 — External/consequential | Publish, contact customer, change access, alter production | Explicit approval and scoped execution grant |
| T4 — High impact/destructive/financial | Spend money, delete critical data, destructive migration, financial commitment | Named owner/authorised approver, strong confirmation and independent safeguards |

Risk classification must consider impact, reversibility, data sensitivity and blast radius, not merely the tool name. A human approval does not legalise an otherwise prohibited action.

### 9.4 Approval lifecycle

An approval record SHOULD contain: `approval_id`, tenant, requester, proposed action, exact resource/scope, risk tier, evidence/reason, approver, decision, timestamp, expiry, conditions, policy version and execution linkage.

Approval MUST bind to the exact action and parameters reviewed. Material changes to action, resource, amount, destination, scope or timing MUST invalidate the approval or require re-approval. Approvals MUST expire and MUST NOT be transferable to unrelated tasks.

## 10. Runtime identity and binding contract

### 10.1 Mandatory NODE01 invariant

**NODE01 IS SOFTWARE. NODE01 IS NOT A MACHINE.**

NODE01 is the stable logical software/runtime identity. The execution environment is a separate, independently managed infrastructure resource. The binding connects them without merging their identities.

### 10.2 Proposed runtime binding

```json
{
  "runtime_binding_id": "rbind_example",
  "logical_node_id": "NODE01",
  "identity_type": "software-runtime",
  "runtime_host_is_separate": true,
  "execution_environment": {
    "execution_environment_id": "execenv_example",
    "environment_type": "containerised",
    "locator_ref": "fortress-protected-environment-reference"
  },
  "binding_status": "unverified",
  "verified_at": null,
  "verification_evidence_ref": null,
  "binding_version": "1",
  "created_at": "2026-11-26T05:00:00Z"
}
```

This example is intentionally unverified. The locator is a protected reference, not a secret or a public hostname.

Requirements:

- `logical_node_id` MUST remain the software identity and MUST NOT be derived from infrastructure.
- `identity_type` MUST be `software-runtime` for NODE01.
- `runtime_host_is_separate` MUST be true.
- The execution environment MUST have its own identifier and lifecycle.
- The runtime binding MUST be explicit, scoped and versioned.
- A locator MUST be resolved through an approved protected mechanism; do not expose credentials or private connection details in general APIs.
- Only a verified binding with current evidence may satisfy production-promotion requirements.
- Missing, stale, ambiguous or contradictory binding evidence MUST fail closed.
- Replacing, scaling or retiring an execution environment MUST NOT regenerate NODE01's identity.
- Multiple environments may support the same logical software identity only where the runtime architecture explicitly supports that topology and its coordination semantics are defined.

### 10.3 Binding lifecycle

Proposed states: `unverified`, `verified`, `suspended`, `retired`.

Allowed transitions require an auditable operation and evidence. For example, `unverified → verified` requires a successful verification procedure against the intended environment. `verified → suspended` blocks new production promotion until re-verification. `retired` is terminal for that binding record; replacement creates a new binding record and does not alter NODE01 identity.

## 11. Command and idempotency contract

Commands represent requested operations; they are not events and do not prove that an operation occurred.

Proposed command metadata:

```json
{
  "command_id": "cmd_example",
  "command_type": "experience.case.assign",
  "schema_version": "1.0",
  "tenant_id": "tn_example",
  "actor": {
    "actor_type": "agent",
    "actor_id": "agt_example",
    "principal_id": "prn_example"
  },
  "purpose": "support.case_resolution",
  "correlation_id": "cor_example",
  "idempotency_key": "tenant-scoped-client-generated-key",
  "requested_at": "2026-11-26T05:00:00Z",
  "resource": {
    "resource_type": "experience.case",
    "resource_id": "case_example"
  },
  "payload": {
    "assignee_ref": "usr_assignee_example"
  }
}
```

Requirements:

- Side-effecting commands MUST carry an idempotency key scoped to tenant, command type and caller/client.
- Repeating the same key and semantically identical request MUST return the original logical result, not perform a duplicate side effect.
- Reusing a key with a different request body MUST be rejected as an idempotency conflict.
- The deduplication record and side effect SHOULD be committed atomically where supported, or reconciled through an explicit durable workflow.
- Idempotency retention MUST be documented and cover the advertised retry window.
- Commands MUST validate tenant, actor, purpose, resource ownership and FORTRESS authorisation before mutation.
- Long-running commands SHOULD return a durable task/job reference and expose explicit states rather than hold an unbounded request open.

## 12. Standard error contract

Errors MUST be structured, machine-readable and safe to expose to the caller.

```json
{
  "error": {
    "code": "AUTHORIZATION_DENIED",
    "message": "The requested operation is not permitted.",
    "correlation_id": "cor_example",
    "retryable": false,
    "details": {
      "policy_decision_ref": "pdec_example"
    }
  }
}
```

Initial error-code vocabulary:

| Code | Meaning | Retry guidance |
|---|---|---|
| `INVALID_REQUEST` | Malformed or invalid schema | Correct request; do not retry unchanged |
| `UNAUTHENTICATED` | Principal not authenticated | Re-authenticate |
| `AUTHORIZATION_DENIED` | Policy denied operation | Do not retry without changed authority |
| `APPROVAL_REQUIRED` | Approval gate not satisfied | Obtain exact required approval |
| `TENANT_CONTEXT_REQUIRED` | Tenant context missing | Supply verified context |
| `RESOURCE_NOT_FOUND` | Resource absent or intentionally undisclosed | Verify reference and scope |
| `IDEMPOTENCY_CONFLICT` | Key reused with different request | Use a new key for a new logical command |
| `PRECONDITION_FAILED` | State/version/binding precondition failed | Refresh state and re-evaluate |
| `DEPENDENCY_UNAVAILABLE` | Required dependency unavailable | Retry only under bounded backoff |
| `RATE_LIMITED` | Caller/service rate limit reached | Honour retry guidance |
| `INTERNAL_ERROR` | Unexpected failure | Retry only if operation is idempotent |

Messages MUST NOT disclose whether a protected resource exists when doing so would leak information. Stack traces, secret values, tokens, private network details and sensitive payloads MUST NOT be returned to ordinary callers.

## 13. Audit record contract

Security-relevant access, policy decisions, approvals, configuration changes and consequential actions MUST produce audit evidence.

A logical audit record SHOULD include:

- unique `audit_id`;
- tenant and classification;
- actor and authenticated principal;
- action and resource reference;
- purpose and correlation/causation identifiers;
- policy ID/version and decision reference;
- approval reference and approver where required;
- outcome (attempted, succeeded, failed, denied);
- timestamp and source service/version;
- minimal before/after metadata or protected change reference;
- integrity/protection metadata according to the selected storage design.

Audit records MUST NOT contain secrets or unnecessary raw personal data. Access to audit data itself MUST be controlled and audited. The storage implementation must define tamper resistance, retention, export, deletion/legal-hold handling and integrity verification; this document does not assume a particular database or cryptographic implementation.

## 14. API and event naming conventions

Proposed domain prefixes:

- `signal.*`
- `experience.*`
- `ai_workforce.*`
- `code.*`
- `infrastructure.*`
- `runtime.*`
- `edge.*`
- `fortress.*`
- `connecta.*)
- `jarvis.*`

Event names describe facts that have occurred, preferably in past-tense form: `signal.observation.recorded`, `experience.case.resolution_recorded`, `runtime.binding.verified`.

Command names describe requested intent: `experience.case.assign`, `runtime.binding.verify`, `signal.monitor.start`.

Queries retrieve state and MUST NOT create side effects. If a request can mutate state, it is a command even if exposed through an HTTP endpoint.

## 15. Versioning and compatibility

- Event and command payloads MUST declare a schema version.
- Additive optional fields are generally backward-compatible only when consumers are required to ignore unknown fields safely.
- Changing field meaning, removing required fields, changing security semantics or altering identifier scope is a breaking change.
- Breaking changes require a new major contract version and an explicit migration/deprecation plan.
- Producers MUST NOT silently change payload semantics under an existing version.
- Consumers SHOULD advertise supported versions; producers MUST use a mutually supported version or fail explicitly.
- Schema registry or equivalent source of truth MUST record owner, version, status, compatibility rules and deprecation date.
- Contract tests MUST cover valid examples, invalid examples, unknown fields, tenant isolation, policy denial, duplicate delivery and version compatibility.

## 16. Minimum conformance test catalogue

A service claiming conformance to these contracts must provide automated evidence for the applicable cases:

1. Reject missing or unverified tenant context on tenant-scoped operations.
2. Reject caller-supplied tenant IDs that do not match authenticated membership.
3. Reject unauthenticated principals and expired credentials.
4. Deny by default when FORTRESS is unavailable or policy cannot be evaluated.
5. Enforce policy obligations and exact approval scope.
6. Reject approval reuse after material command parameters change.
7. Preserve actor, tenant, purpose, correlation and provenance across asynchronous work.
8. Reject invalid event schema versions and malformed payloads.
9. Process duplicate event IDs without duplicate side effects.
10. Reject idempotency-key reuse with a different request.
11. Preserve the distinction between observation, interpretation, recommendation, decision, action and outcome.
12. Prevent secrets from entering events, audit records and ordinary logs.
13. Keep NODE01 identity separate from execution-environment identifiers and locators.
14. Block production promotion for unverified, stale or contradictory runtime bindings.
15. Ensure cross-tenant access is denied absent an explicit audited grant.
16. Verify audit evidence for policy decisions, approvals and consequential operations.
17. Verify version compatibility and explicit handling of unsupported versions.
18. Verify retries, dead-letter handling and replay provenance for event consumers.

Tests must run against the actual service boundary and policy implementation; unit tests alone are insufficient for claims about tenant isolation or production authority.

## 17. Implementation sequence and ownership

The following sequence is recommended. It is not an implementation status report.

| Work package | Deliverable | Dependency |
|---|---|---|
| A — Vocabulary and schema registry | Canonical identifiers, event types, schema ownership/version policy | Architecture review |
| B — Tenant and actor context | Authenticated tenant resolution and delegation semantics | FORTRESS identity model |
| C — Event and command contracts | Machine schemas, transport mapping, idempotency and replay tests | A, B |
| D — Evidence model | Provenance, lifecycle and classification schemas | A, B |
| E — FORTRESS policy interface | Decision/obligation/approval contract and conformance suite | B, D |
| F — Runtime binding | NODE01 identity separation, environment inventory and verification workflow | FORTRESS, Runtime Fabric |
| G — Cross-domain pilots | One SIGNAL and one EXPERIENCE workflow using common contracts | A–F as applicable |

Every contract must have a named domain owner, platform/security reviewer and test owner before implementation is promoted. The actual service locations and persistence choices must be established by repository inspection and approved ADRs rather than inferred from this document.

## 18. Open decisions requiring ADRs

1. Canonical identifier generation and collision/namespace strategy.
2. Authoritative tenant membership source and service-to-service identity.
3. Delegation and agent-on-behalf-of semantics.
4. Event transport, schema registry and replay retention.
5. Atomicity boundary for idempotency records and side effects.
6. FORTRESS policy language, decision API and approval provider.
7. Audit storage integrity, retention and lawful deletion model.
8. Evidence storage and source-licensing metadata.
9. Runtime environment inventory, protected locator resolution and binding verification procedure.
10. Cross-domain data access and analytics projection rules.

No choice in this list is silently resolved by the example payloads.

## 19. Non-goals and safety boundaries

This document does not:

- create or migrate database tables;
- implement APIs, queues, schemas or policy engines;
- change FORTRESS permissions or issue credentials;
- bind NODE01 to an execution environment;
- provision, purchase or activate infrastructure or third-party services;
- authorise agents to publish, contact customers, spend funds or change production;
- certify POPIA, security or other regulatory compliance;
- claim any proposed contract is deployed, tested or production-ready.

All such work requires separate implementation plans, owner approval, repository-level inspection and verifiable acceptance evidence.

## 20. Definition of contract readiness

The shared contract baseline is ready to guide implementation when:

- the architecture dependency has been reviewed and accepted;
- identifier and vocabulary ownership is assigned;
- each proposed shape has a machine-readable schema and examples;
- tenant and actor resolution semantics are testable;
- FORTRESS policy and approval contracts have deny-by-default conformance tests;
- event delivery and idempotency semantics are explicit for selected transports;
- evidence provenance and classification are validated;
- NODE01 runtime binding can be verified without conflating software identity and infrastructure;
- audit, retention and privacy handling are reviewed;
- at least one cross-domain pilot demonstrates the contracts end to end without bypassing domain ownership.

A completed specification is not proof of implementation. A passing contract test is not proof of production readiness. Production promotion remains subject to the ecosystem architecture's deployment and governance gates.
