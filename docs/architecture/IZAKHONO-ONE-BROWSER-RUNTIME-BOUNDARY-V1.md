# IZAKHONO ONE — Browser Runtime Boundary V1

**Status:** Proposed architecture; documentation only  
**Product:** IZAKHONO ONE v1.0  
**Scope:** Browser process boundary, session lifecycle, request protocol, cancellation and audit  
**Upstream reference:** n8n-io/nod, reviewed at release source commit `0c3e0ff651d71cc6c4a6676b62ce2aa6ee938394` (Nod v0.9.5)  
**Decision:** Reuse architectural lessons only. No Nod source code or binary is adopted by this document.

## 1. Decision

IZAKHONO ONE will own its browser-runtime contract and policy. A browser is a separately isolated capability, not an extension of the agent's shell, workspace or host privileges.

The first implementation target is a disposable, read-only browser session. The session manager, policy enforcement and audit ledger belong to IZAKHONO-controlled services. Chromium and its driver are replaceable providers behind an IZAKHONO-owned port.

No model instruction, web page, downloaded content or browser result can grant authority or override server-side policy.

## 2. Trust zones

| Zone | Responsibility | Must not receive |
|---|---|---|
| IZAKHONO policy/control service | Owner identity, task authority, policy decisions, session issuance, audit | Untrusted page scripts as executable instructions |
| Agent runtime/workspace | Task planning and interpretation of observations | Provider secrets, host control socket, browser container privileges |
| Browser runtime | Render and inspect pages within a disposable isolated session | Model/provider keys, FORTRESS secrets, host filesystem, workspace mounts, Docker socket |
| Network enforcement boundary | Resolve and constrain destination addresses; block private, reserved and metadata ranges | Authority to widen policy |
| Audit store | Append structured lifecycle and policy evidence | Passwords, tokens, cookies, full page bodies or unnecessary personal data |

The browser must not share a filesystem mount or network namespace with the agent workspace. The browser must not be able to reach the control database, host services, cloud metadata endpoints, private LANs or other session containers.

A narrow authenticated local IPC bridge is permitted. It must validate message schemas, bind each request to an authorised session and task, enforce message-size limits, and reject unknown methods. The bridge is not a general-purpose shell or host-command interface.

## 3. Session lifecycle

Each browser session is ephemeral by default and bound to:
- an opaque session ID generated by the control service;
- one owner/tenant identity;
- one authorised task ID and execution-environment identity;
- one policy profile and capability set;
- creation and absolute expiry timestamps;
- a unique runtime/container instance identifier.

Required lifecycle states:

`REQUESTED -> AUTHORISED -> STARTING -> READY -> RUNNING -> CLOSING -> CLOSED`

Terminal alternatives: `DENIED`, `FAILED`, `EXPIRED`, `CANCELLED`, `QUARANTINED`.

Rules:
1. A session cannot start until policy authorisation and the isolated runtime are both ready.
2. Session IDs are not credentials. Every bridge request must also authenticate the caller and validate owner, task, runtime and policy bindings.
3. A session cannot be rebound to another owner or task.
4. A task timeout, owner cancellation, policy revocation or bridge-integrity failure aborts pending work.
5. Closing aborts pending requests, terminates the browser process tree, removes the ephemeral profile and temporary files, closes IPC, and records the terminal result.
6. If process termination or cleanup cannot be confirmed, mark the session `QUARANTINED`; do not silently reuse its runtime or storage.
7. Sessions are not automatically resumed after uncertain cancellation or a lost bridge response. A new authorised session is required.
8. Multiple sessions must have independent profiles, process groups, storage and resource limits.

## 4. Request contract

The initial read-only profile permits only:
- `navigate` to a destination approved by the network policy;
- `snapshot` or `extract_text` of the current page;
- `wait` within a bounded timeout;
- `close` / `cancel`.

It does not permit click, type, fill, submit, upload, download, sign-in, cookie changes, JavaScript evaluation, arbitrary file access, shell commands or browser extension installation.

Every request includes:
- protocol version;
- request ID;
- session ID;
- owner/tenant ID;
- task ID;
- execution-environment ID;
- issued-at and deadline;
- method and strictly validated arguments;
- policy profile/version.

The runtime returns a structured result with request ID, session ID, outcome, bounded observation, elapsed time and safe error code. It must not return credentials, cookies, raw browser profile data or hidden page state.

Unknown fields and methods are rejected. No implicit retries are permitted for requests with uncertain outcomes.

## 5. Network security requirements

The existing URL-policy module is a preliminary syntactic guard, not an SSRF defence and not a production network boundary.

Before public browsing is enabled, all of the following are mandatory:

1. Resolve every hostname using a controlled resolver immediately before connection.
2. Reject the destination if any returned A or AAAA address is private, loopback, link-local, unique-local, multicast, reserved, documentation-only, unspecified, or otherwise non-public.
3. Pin the validated address to the actual connection. Do not validate one DNS answer and then allow the browser to resolve the hostname independently.
4. Revalidate every redirect and every new navigation, including subresources, WebSockets, downloads and popup targets.
5. Enforce the same restrictions at a network firewall/egress proxy outside Chromium. The browser must not be able to bypass it with direct sockets, DNS-over-HTTPS, QUIC or alternate protocols.
6. Block cloud metadata endpoints and internal control-plane destinations explicitly.
7. Prevent DNS rebinding and IPv4/IPv6 transition-address bypasses.
8. Restrict ports and protocols to an explicit allowlist.
9. Record the policy decision and destination class without storing sensitive query strings unnecessarily.

A URL parser check alone is never sufficient. Public navigation remains disabled until DNS pinning, address classification, redirect/subresource enforcement and external egress controls are implemented and tested.

## 6. Browser process isolation

Production browser runtime requirements:
- dedicated unprivileged container or equivalent OS sandbox per isolated session (or a rigorously isolated session pool with separate process, profile and namespace boundaries);
- no host networking, host PID namespace, privileged mode, host mounts or container-runtime socket;
- read-only root filesystem where practical; bounded writable temporary storage;
- dropped Linux capabilities, no-new-privileges, seccomp and mandatory access controls where supported;
- CPU, memory, process-count, file-size, open-file and wall-clock limits;
- browser process-tree supervision and forced termination on deadline;
- patched, pinned browser and driver versions with provenance and vulnerability review;
- no provider keys, application tokens or FORTRESS credentials in browser environment variables, command line, filesystem or IPC payloads.

Chromium's internal sandbox must remain enabled where the supported runtime permits it. If a platform requires a different isolation strategy, that strategy must be independently reviewed; a container must not be assumed to make disabling Chromium's sandbox safe.

## 7. Policy and action authority

The policy service, not the agent prompt, decides what a session may do.

For v1 read-only mode, policy can authorise observation only. Any future interactive capability requires a separately reviewed action taxonomy:
- read/observe;
- private preparation;
- reversible state change;
- consequential external commitment;
- sensitive credential or payment action.

A page's content is untrusted data. It cannot authorise an action, change a policy profile, request secrets, or instruct the runtime to bypass controls. A user approval must be bound to the exact proposed action, target and material arguments. Approval for one action is not blanket permission for subsequent actions.

## 8. Audit event envelope

The audit ledger is append-only and records at minimum:
- `event_id`, `event_type`, `occurred_at`;
- `owner_id`, `task_id`, `session_id`, `runtime_instance_id`;
- `policy_id`, `policy_version`, `decision`, `reason_code`;
- `request_id`, `method`, `destination_origin` (when relevant);
- `duration_ms`, `resource_usage` (when available);
- `result_code`, `cleanup_status`, `correlation_id`.

Required event types include:
`session.requested`, `session.authorised`, `session.denied`, `runtime.started`, `runtime.ready`, `request.accepted`, `request.completed`, `request.rejected`, `request.timed_out`, `session.cancelled`, `runtime.terminated`, `profile.destroyed`, `session.closed`, `session.quarantined`.

Do not log passwords, authentication codes, cookies, access tokens, payment data, full request/response bodies, or page text by default. Audit evidence should prove what happened without becoming a second credential store.

## 9. Nod upstream assessment

The reviewed Nod architecture provides useful patterns:
- separate browser container and workspace container;
- a narrow stdin/Unix-socket bridge;
- server-owned trust decisions;
- per-session browser state;
- explicit deadlines and process termination;
- public-address enforcement outside ordinary page instructions.

Nod also has a mature, broader interactive browser surface, including sign-in, file transfer and consequential actions. Those capabilities are outside IZAKHONO ONE's initial read-only scope.

Adoption decision:
- do not adopt Nod as the IZAKHONO control plane;
- do not copy or vendor source at this stage;
- do not install Nod, Chromium, agent-browser or any runtime dependency as part of this documentation increment;
- retain the upstream release and commit as review provenance;
- reconsider component reuse only after exact source, licence/NOTICE, dependency, build, security and maintenance reviews.

## 11. Cost and change controls

This document authorises no spending, subscription, package installation, container image pull, compute provisioning, account connection, credential handling, production browser launch, deployment, DNS change, merge or production migration.

The session-contract increment is now present as a dependency-free in-memory reference state machine with deterministic Node test cases. It binds sessions to owner, task and execution environment; checks policy version and request deadlines; permits only the read-only request methods; correlates completions; and requires explicit process-tree, profile and IPC cleanup confirmation. It is a contract/test harness, not a durable production session manager or runtime supervisor. CI validation for the latest commit remains unconfirmed. Any dependency, host runtime, infrastructure or production change requires separate explicit approval.

## 12. Runtime supervisor reference implementation

A dependency-free reference supervisor now exists at `products/izakhono-one/agent-browser/runtime-supervisor.mjs`. It accepts an injected runtime driver and coordinates the existing session registry. The narrow driver contract exposes only runtime creation, readiness probing, bounded read-only dispatch, process-tree termination, profile destruction and IPC closure. It does not expose shell execution, arbitrary host commands or generic IPC.

The supervisor binds a runtime instance to the authorised session, owner, task and execution environment; rejects write-capable methods and policy-version mismatches; enforces request deadlines and result-size bounds; and does not retry uncertain dispatches. A lost bridge response, timeout or oversized result quarantines the session and triggers cleanup. Cleanup evidence separately records process-tree, profile and IPC outcomes. Incomplete cleanup retains a quarantine record.

The implementation is deliberately a reference orchestration contract. The injected driver is not yet implemented. No operating-system process, container, Chromium instance, network namespace, firewall, DNS resolver or browser profile was created or tested. The current fake-driver tests verify orchestration decisions only; they do not prove operating-system isolation or safe network egress.

The browser policy test command now includes the supervisor suite. CI for the current head must be checked before describing any suite as passing. This increment authorises no dependency installation, container image pull, runtime launch, infrastructure spend or deployment.

## 13. Isolation policy and attestation gate

`products/izakhono-one/agent-browser/isolation-policy.mjs` defines the minimum runtime controls and validates a controller-signed isolation attestation. The supervisor does not mark a runtime READY until the attestation binds the exact session, runtime instance and policy version, has an accepted signature through an injected trusted verifier, and asserts all mandatory controls, uses the exact isolated-egress-proxy-only network mode, and falls within its signed validity window.

The required controls include a dedicated unprivileged identity, read-only root filesystem, per-session ephemeral profile, no host mounts or host IPC, no privileged mode, dropped capabilities, no-new-privileges, reviewed seccomp enforcement, resource limits, process-tree supervision, authenticated narrow bridge, runtime deadlines, egress firewall, DNS/IP pinning, private/reserved/metadata address blocking, and profile destruction.

The attestation validator is only as trustworthy as its injected signature verifier and the controller producing the evidence. A test verifier is used in unit tests only. No production signing key, runtime controller, container profile, seccomp policy, firewall or network proxy has been implemented or deployed. The policy declaration is not proof that a running environment enforces these controls.

A production runtime adapter must implement and independently test each control, sign evidence from a trusted controller, and fail closed when evidence is missing, stale, mismatched or unverifiable. The next gate is a reviewed, platform-specific runtime adapter plus integration tests in an isolated environment; public navigation remains disabled until DNS/IP pinning and egress enforcement are real.
