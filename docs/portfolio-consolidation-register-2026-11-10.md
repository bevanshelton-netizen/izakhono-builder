**Important:** The categories below are provisional **name-based workstream assignments**, not proof that two applications have the same code or can be merged. No destructive changes, customer migrations, production promotions, domain transfers, data merges or archive actions are authorised by this register alone.

## Product positioning and consolidation rules

1. Keep a distinct product when it has different customers, regulatory exposure, content rights, brand equity or ownership.
2. Merge *capabilities* first: common identity/tenant, iKhokha-compatible payment orchestration, provisioning, CRM, content/media, AI orchestration, analytics, monitoring and support.
3. Consolidate Vercel projects only after comparing GitHub source, root directory, env variable **names** (never values), database, domains, active users, backups and traffic; prove migration and rollback.
4. IZAKHONO-owned infrastructure remains preferred. External Vercel/GitHub deployments are retained as reversible fallbacks until owned runtime, TLS, backup and health checks pass.
5. Classify each record with one of: **canonical product**, **shared component**, **staging**, **preview**, **experiment**, **duplicate candidate**, **archive candidate**, **unknown** after evidence gathering.
6. Complete = verified code + tests + security + integrations + production deployment + domains + payment controls (where applicable) + observability + backups + documentation + handover.

## Canonical target architecture

- **IZAKHONO CORE:** owned-first repository, hosting/provisioner, customer identity and tenancy, billing/entitlements, audit/monitoring, support and deployment automation.
- **IZAKHONO BUILDER:** flat-rate website/app creation and controlled release-candidate pipeline.
- **IZAKHONO COMMERCE:** shared storefront, checkout, subscription and invoicing components, not a forced merger of independent merchants.
- **IZAKHONO MEDIA:** reusable creator, publishing, rights, streaming and analytics capabilities; Allegro, KORA, YHVH and others remain independent brands.
- **IZAKHONO LEARNING:** shared course/enrolment/assessment engine; Edu-Build, FAISReady and other learning brands keep separate enrolment, regulatory and data boundaries.
- **IZAKHONO SECURITY:** FORTRESS security core with explicit tenant and product boundaries.
- **IZAKHONO MOBILITY:** NAV core; freight/aviation operations remain separate commercial and regulatory businesses.
- **INDEPENDENT PRODUCTS:** keep separate products wherever merging would create legal, brand, data, safety or operational risk.

### Wave 0 — Source mapping and safety
- Match every project ID to Git repository/branch/root directory/commit, production deployment, domain, protection mode, database and environment names.
- Confirm any data in inactive Supabase projects before changes.
- Identify the canonical implementation and dependency graph; preserve active releases.

### Wave 1 — Shared platform
- Complete Builder, Website Factory, WebStart and Provisioner contracts.
- Validate a complete **test customer** purchase → payment confirmation → tenant creation → site provisioning → DNS/TLS → welcome email → admin login.
- Add a signed payment webhook, idempotency, reconciliation, rate limits, audit trail, backup and rollback.

### Wave 2 — Independent products
- Bring products through a standard gate: tests, privacy/security, production smoke, operational handover.
- Pilot one product at a time. Verify rights, safeguarding, payments and regulatory requirements as appropriate.

### Wave 3 — Controlled consolidation
- Only merge verified duplicate implementations after backup and cutover tests.
- Keep aliases and redirects; do not delete active projects until telemetry and rollback acceptance.
