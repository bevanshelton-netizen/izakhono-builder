# IZAKHONO AFRICA mail DNS deployment worksheet

Domain: izakhonoafrica.co.za
Mail host: mail.izakhonoafrica.co.za
Webmail: webmail.izakhonoafrica.co.za
Public IP: replace only after the mail node has a verified static public IPv4.

Do not apply this worksheet until the existing DNS zone has been exported and all current MX, SPF, DKIM and third-party senders have been inventoried. Do not replace an existing SPF record blindly.

## Ownership verification

The self-hosted mail control plane first issues a unique TXT challenge:

- Name: _izakhono-verify.izakhonoafrica.co.za
- Value: izakhono-verification=<one-time value returned by /api/domains/verification>

Publish the exact value returned by the API. After DNS propagation, call /api/domains/verify. Mail domain and mailbox creation are blocked until this check succeeds.

## Required service records

| Type | Name | Value |
|---|---|---|
| A | mail | <STATIC_PUBLIC_IPV4> |
| A | webmail | <STATIC_PUBLIC_IPV4> |
| A or CNAME | autoconfig | mail.izakhonoafrica.co.za |
| A or CNAME | autodiscover | mail.izakhonoafrica.co.za |
| A | mta-sts | <STATIC_PUBLIC_IPV4> |
| MX | @ | 10 mail.izakhonoafrica.co.za |

Reverse DNS/PTR for the static public IP must resolve to mail.izakhonoafrica.co.za.

## Authentication and transport policy

- SPF: merge the IZAKHONO mail server's sending IP with every legitimate existing sender. Start with a monitored soft-fail policy; do not publish -all until all senders are accounted for.
- DKIM: publish the exact selector and public key generated by the live Stalwart instance. Never use a guessed selector or key.
- DMARC: begin with p=none and aggregate reports to dmarc-reports@izakhonoafrica.co.za. Move to quarantine/reject only after reports show alignment.
- MTA-STS TXT at _mta-sts: v=STSv1; id=20261114
- TLS-RPT TXT at _smtp._tls: v=TLSRPTv1; rua=mailto:dmarc-reports@izakhonoafrica.co.za

The HTTPS policy file is served at:
https://mta-sts.izakhonoafrica.co.za/.well-known/mta-sts.txt

The current policy is mode: testing. Change to enforce only after inbound/outbound SMTP TLS and delivery tests pass.

## Migration and rollback

1. Keep the current Hostinger mail service and MX records active.
2. Verify the IZAKHONO domain ownership TXT challenge.
3. Create and test the mailbox on Stalwart without changing MX.
4. Test outbound delivery to independent providers and inbound delivery using a temporary test subdomain or controlled MX test.
5. Migrate existing mailboxes and historical messages.
6. Verify SPF, DKIM, DMARC, TLS, webmail and client access.
7. Change MX only after written acceptance.
8. Retain the old provider and its DNS records during the rollback window.
